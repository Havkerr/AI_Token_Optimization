# AI Model Comparison Tool — Phase 1

## 1. Objective

Build a simple web-based AI Model Comparison Tool.

The purpose of Phase 1 is to compare multiple LLM models using the **same prompt** and collect basic performance data.

The system should answer:

> How do different AI models compare in terms of cost, token usage, response time, and user preference?

This is a data-collection phase.

**Do NOT implement AI model recommendation, ML-based routing, semantic caching, context optimization, or automatic complexity detection in Phase 1.**

---

# 2. Core User Flow

The user should be able to:

1. Enter a prompt.
2. Select 2–3 available AI models.
3. Click "Run Comparison".
4. Backend sends the same prompt to each selected model.
5. Display each model's response.
6. Display basic metrics for each response.
7. User rates each response as:

   * Good
   * Bad
8. Save all data to the database.

---

# 3. Basic UI

Create a simple dashboard.

## Prompt section

Fields:

* Prompt textarea
* Model selection
* Run Comparison button

Example:

Prompt:

"Explain recursion to a beginner with an example."

Models:

* Model A
* Model B
* Model C

Button:

"Run Comparison"

---

# 4. Results

After execution, show one result card/table row per model.

For each model display:

* Model name
* Generated response
* Input tokens
* Output tokens
* Total tokens
* Estimated cost
* Response latency
* User rating

User rating:

* Good
* Bad

The user should be able to rate each model independently.

---

# 5. Comparison Summary

After all models finish, show a simple summary.

Example:

* Cheapest model
* Fastest model
* Lowest token usage
* User-preferred model

Also show basic comparisons such as:

"Model A was 70% cheaper than Model B."

Do not make recommendations about which model should be used for a task.

The system is only reporting observed results.

---

# 6. Backend

Create a backend API responsible for:

* Receiving prompts
* Receiving selected models
* Calling the selected LLM providers
* Measuring latency
* Obtaining token usage
* Calculating estimated cost
* Returning responses
* Saving results
* Saving user feedback

The frontend should NOT directly call the LLM providers.

---

# 7. Model Abstraction

Create a common interface for models/providers.

The application should be able to call different providers through the same backend abstraction.

Conceptually:

Model request:

* prompt
* model
* configuration

Model response:

* response text
* input tokens
* output tokens
* total tokens
* latency
* cost
* error status

Keep the provider-specific implementation isolated.

This will make adding additional models later easier.

---

# 8. Cost Calculation

Create a centralized cost calculation component.

For each model, maintain:

* Input token price
* Output token price

Calculate:

Input cost:

input_tokens × input_price

Output cost:

output_tokens × output_price

Total:

input cost + output cost

Do not hardcode pricing throughout the application.

Store model pricing in one configuration/database location so it can be updated later.

---

# 9. Database

Keep the database simple.

## prompts

Fields:

* id
* prompt_text
* created_at

## model_runs

Fields:

* id
* prompt_id
* model_name
* response_text
* input_tokens
* output_tokens
* total_tokens
* latency_ms
* estimated_cost
* status
* error_message
* created_at

## feedback

Fields:

* id
* model_run_id
* rating
* created_at

Rating values:

* good
* bad

---

# 10. Dashboard

Create a simple dashboard showing historical data.

Basic metrics:

* Total prompts evaluated
* Total model runs
* Total estimated cost
* Average latency
* Average tokens
* Overall Good/Bad percentage

Also provide a history table:

* Prompt
* Date
* Models tested
* Cost
* Ratings

The dashboard does not need advanced charts in Phase 1.

Simple tables and a few summary numbers are sufficient.

---

# 11. Error Handling

If one model fails:

* Do not fail the entire comparison.
* Display an error for that model.
* Continue showing successful model results.
* Save the failed run with its error status.

Example:

Model A → Success

Model B → Success

Model C → API Error

The comparison should still be usable.

---

# 12. Configuration

API keys must NOT be placed in frontend code.

Use environment variables for provider credentials.

Example:

* LLM_PROVIDER_API_KEY
* DATABASE_URL

Use a `.env` file locally.

Provide a `.env.example` file.

Never commit actual API keys.

---

# 13. Technology

Use a simple, maintainable stack.

Recommended:

Frontend:

* React
* TypeScript

Backend:

* Python
* FastAPI

Database:

* PostgreSQL

ORM:

* SQLAlchemy

Infrastructure:

* Docker / Docker Compose

Use whatever equivalent technologies are already configured in the repository if a project repository exists.

---

# 15. Important Design Principle

The application should collect reliable raw data.

For every model execution, we want:

Prompt
→ Model
→ Tokens
→ Cost
→ Latency
→ Response
→ Human feedback

This dataset will become the foundation for future phases.

Do not prematurely build intelligence on top of insufficient data.

---

---

# 17. Phase 1 Definition of Done

Phase 1 is complete when the following works end-to-end:

1. User enters a prompt.
2. User selects multiple models.
3. Backend sends the same prompt to all selected models.
4. Responses are displayed.
5. Token usage is captured.
6. Cost is calculated.
7. Latency is captured.
8. User can rate each response.
9. Results are stored in PostgreSQL.
10. Historical comparisons can be viewed from the dashboard.
11. Provider/API errors are handled gracefully.
12. No API keys are exposed to the frontend.

The priority is **correctness and clean data collection**, not feature quantity.
